# 阶段 2：RS01 驱动及主动反馈

## 目标

阶段 2 将阶段 1 中仍然混杂的 RS01 协议、全局反馈和裸 CAN ID，收敛为适合 ESP32 的最小双执行器驱动：

- 两个静态执行器对象，对应逻辑槽 `A/B`；
- 只有驱动理解 RS01 私有扩展帧和遗留 MIT 标准帧；
- 每台执行器分别保存有效反馈、时间戳、序号、故障和在线状态；
- 上电后配置 10 ms 周期并请求两台 RS01 主动上报；
- 现有控制台和正弦阻抗基线只做驱动调用适配，不修改算法或参数。

本阶段的“主动上报”是 `RS01 -> ESP32`。`ESP32 -> 手机` 的产品遥测属于阶段 10。

## 阶段边界

阶段 2 不建立人体髋关节对象，不猜测 `A/B` 的人体左右侧，不换算安装方向，也不建立软件零位。以下内容继续留给后续阶段：

- 髋关节对象和软件零位（阶段 3）；
- 唯一 100 Hz 控制任务（阶段 4）；
- 系统状态机和产品 START/STOP（阶段 5）；
- 产品 BLE 协议（阶段 6）；
- 正弦参考和阻抗控制律重构（阶段 7）；
- 产品级统一五元关节命令（阶段 8）；
- 步态估计、相位曲线和产品遥测（阶段 9-10）。

现有阻抗模块允许从旧函数名迁移到新驱动 API，但其 100 Hz 定时器、0.5 Hz 正弦、五次渐入、幅值、增益和启停顺序保持不变。

## 手册依据与已确认差异

协议以 `RS01User Manual260713.pdf` 为主，并与阶段 0/1 实机结果交叉确认。页码格式为“PDF 物理页 / 手册印刷页”。

| 项目 | 依据或结论 |
|---|---|
| 私有协议 | CAN 2.0、1 Mbps、29-bit 扩展帧，PDF 41 / 40 |
| 扩展 ID | type `[28:24]`、data2 `[23:8]`、destination `[7:0]` |
| 运动/反馈量程 | 位置 ±12.57 rad、速度 ±44 rad/s、转矩 ±17 N·m、Kp 0..500、Kd 0..5，PDF 42 / 41 |
| 主动上报开关 | type 24；开启后的周期流为 type 2，PDF 47 / 46、PDF 51 / 50 |
| 上报周期 | `0x7026 EPScan_time`，值 1 为 10 ms，其后每级增加 5 ms，PDF 49 / 48 |
| 详细故障 | type 21，fault 为 Byte0..3，warning 为 Byte4..7，PDF 46 / 45 |
| MIT 反馈 | 标准帧 ID 为 Master ID，Byte0 为来源电机 ID，PDF 71-72 / 70-71 |

阶段 1 的泛型 `MOTOR_TYPE=5` 使用速度 ±50 rad/s、转矩 ±5.5 N·m，与 RS01 手册冲突。阶段 2 改为 RS01 固定量程。该修正不会改变当前阻抗基线的参考运动，因为基线命令中的目标速度和前馈转矩均为 0。

手册本身存在以下歧义，驱动按“表格 + 已验证实机行为”处理：

1. type 24 的 payload 表只列出七个字节，未解释 Byte7；阶段 0/1 已验证的 Byte7=`0x08` 保留。
2. 手册正文将周期流描述为 type 2，但当前两台产品电机实测持续周期帧为 type 24；驱动分别计数并接受两者，不能只按 type 2 判定在线。
3. 手册写明 `0x7026=1` 对应 10 ms，但当前产品固件读回 1 时实测约 15 ms；写入 0 后 A/B 分别测得约 101.05 Hz 和 99.50 Hz。因此阶段 2 对当前产品把 10 ms 映射为 0，之后每增加 5 ms 寄存器值加 1。该实机覆盖只适用于当前固件，后续更换电机固件必须重测。
4. type 21 的两个 `uint32` 未明确字节序；实现暂按参数协议惯例使用 little-endian 解析。只有实际收到 type 21 故障帧后才能确认，并把结果写入验收记录；本阶段不把未触发故障视为已验证字节序。
5. 手册的 `motor_enable()` 示例把已经写入的 Master ID 又覆盖为 0，这是示例错误；驱动保留已经实机验证的 Master ID。
6. 参数表把 `CAN_MASTER` 最大值写为 127，但示例、MIT Host ID 和当前实机均使用 `0xFD`；阶段 2 不修改已验证的 Master ID。

## 最小对象模型

驱动内部只保留固定大小的静态数组：

```c
static rs01_motor_t s_motors[EXO_ACTUATOR_COUNT];
```

每个对象保存：

- 逻辑槽和当前配置 CAN ID；
- 最近一次请求的使能、主动上报和控制模式；
- 最新 `exo_motion_sample_t`；
- 运行模式、规范化故障标志、原始 fault/warning；
- 首帧和最近一帧时间戳；
- 有效反馈计数、无效帧计数和最近反馈间隔；
- 有效状态。

维护命令修改 CAN ID 成功后，驱动会在 TX 锁内检查 A/B 冲突并原子更新该逻辑槽的
运行时 ID；硬件配置仍表示下次启动的初始值。若要跨重启保留新 ID，必须同步修改
硬件配置。

对象不公开。上层通过 `rs01_feedback_snapshot_t` 取得一致快照。`online` 不由“命令发送成功”决定，而在读取快照时计算：

```text
valid && now - last_feedback <= feedback_timeout
```

这不需要增加后台任务或软件定时器。

## 驱动接口原则

公共驱动接口全部接收 `exo_actuator_id_t`，不得要求业务模块传入 `0x10/0x20`。接口覆盖：

- 初始化、CAN ID 查询和兼容映射；
- 使能、失能和控制模式；
- RS01 五参数运动帧；
- 参数读写和维护命令；
- 主动上报周期、开启和关闭；
- 独立反馈快照；
- 完整 CAN 帧处理及接收事件。

控制台为了兼容阶段 0/1 脚本，仍可接受 `motor 0x10` 和 `motor 0x20`，但必须立即通过配置映射成 `A/B`；驱动之后只接收逻辑槽。未配置的任意 CAN ID 被拒绝。

## 启动顺序

```text
初始化两个静态 RS01 对象和现有静态 TX 锁
    -> 安装并启动 TWAI
    -> 创建并确认现有 TWAI RX 任务
    -> 为 A/B 写入 10 ms 上报周期
    -> 为 A/B 发送 type 24 开启命令
    -> 启动现有 BLE/UART 控制台
```

主动上报不会使能电机或产生运动。`reporting_requested=true` 只表示发送请求成功；只有收到有效反馈后 `valid/online` 才成立。

## 接收路径

主程序不再解释 RS01 字节：

```text
twai_receive()
    -> rs01_process_can_frame()
        -> 校验 RTR/帧格式/DLC/目的 Master/来源 A-B/type
        -> 解码并原子更新对应对象
        -> 返回通用接收事件和更新的逻辑槽
    -> 主程序按逻辑槽读取快照
    -> 低频 UART 调试日志
```

反馈日志继续节流，但反馈计数和时间戳在每个有效 CAN 帧上更新。实际帧率必须通过计数差除以测量时间计算，不能使用日志行数推断。

CAN RX 任务不直接发送 BLE 通知，因为 BLE 发送可能等待连接缓冲并阻塞 200 Hz
总接收流。阶段 2 的 BLE 调试只保留按需 `motor A/B` + `status` 查询；连续、
非阻塞的产品遥测在阶段 10 实现。

## 并发和资源

- TX 使用原有的一个静态递归 mutex，保证控制台复合命令和现有 100 Hz 回调不会交叉组帧。
- 每个 TX 帧和 payload 都是函数栈上的局部变量，删除共享 TX/RX 缓冲。
- 反馈对象通过一个短 `portMUX` 临界区更新和复制。
- 相对阶段 1 不新增任务、定时器、队列、同步对象或动态分配调用点。
- 高频 RX 路径不逐帧输出日志，只记录状态变化或受控低频调试信息。

## 配置

阶段 2 在唯一 `g_exo_hardware_config` 中增加：

| 配置 | 值 | 含义 |
|---|---:|---|
| `rs01_report_interval_ms` | 10 ms | 当前产品实测周期；驱动写入 `0x7026=0` |
| `rs01_feedback_timeout_ms` | 100 ms | 主机侧在线判断阈值，必须通过实测确认有足够余量 |

CAN ID、Master ID、GPIO、波特率、控制频率和 BLE 名称仍只有阶段 1 的配置对象提供。左右侧、方向和软件零位字段不变。

## 完成标准

1. 只有 `rs01_driver.c` 出现 RS01 功能码、量化和帧布局。
2. A/B 具有独立、无撕裂的反馈快照，不再存在单一全局反馈或 128 项裸 ID 状态表。
3. 上电自动请求两台电机以 10 ms 周期主动上报，并能分别关闭、超时离线和恢复。
4. 实测反馈频率、首帧时间、在线超时、A/B 隔离和 type 21 行为有明确记录。
5. 原有控制台、BLE、使能/失能和 3 x 10 秒阻抗回归通过，TWAI 错误增量为 0。
6. ESP-IDF v5.5 干净构建无 warning/error，镜像不超分区。
7. 相对阶段 1 不新增任务、定时器、队列、同步对象或动态内存调用点。
8. 实际结果记录在 `PHASE_2_ACCEPTANCE.md`，验收通过后创建 `phase2-rs01-driver-feedback` 标签。
